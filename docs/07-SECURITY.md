# Security

---

# Назначение

Подсистема Security
обеспечивает
идентификацию,
аутентификацию
и авторизацию пользователей.

Security
не содержит
бизнес-логики приложения.

Ее задача —

обеспечить безопасный доступ
к функциональности системы.

---

# Основные принципы

Подсистема Security
строится
на следующих принципах.

- минимально необходимые права;

- разделение ответственности;

- отсутствие доверия
  к пользовательскому вводу;

- независимость
  бизнес-логики
  от механизмов безопасности.

---

# Основные компоненты

Подсистема включает:

- Authentication;

- Authorization;

- JWT;

- Refresh Token;

- OAuth2 Client;

- Password Encoder.

---

# Authentication

Authentication
отвечает
за подтверждение личности пользователя.

После успешной проверки

система создает
контекст безопасности.

---

## Поддерживаемые способы

На первом этапе:

- Email + Password.

На последующих этапах:

- GitHub OAuth2.

Архитектура
допускает
добавление
других поставщиков.

---

## Основные принципы

Authentication:

- не определяет права;

- не принимает
  бизнес-решения;

- только подтверждает личность.

---

# Authorization

Authorization
определяет,

какие действия

доступны пользователю.

---

## Роли

На текущем этапе
используются две роли.

- USER

- ADMIN

---

## USER

Имеет доступ
только
к собственным данным.

---

## ADMIN

Имеет право:

- управлять пользователями;

- управлять Source;

- выполнять
  административные операции.

---

## Основные принципы

Авторизация

строится
по принципу

Least Privilege.

Каждый пользователь

получает
только
необходимые права.

---

# JWT

JWT
используется
для аутентификации
REST API.

---

## Назначение

Предоставить
краткоживущий
Access Token.

---

## Основные принципы

JWT:

- не хранится
  в базе данных;

- имеет ограниченный
  срок действия;

- используется
  только
  для подтверждения
  личности пользователя.

---

## Содержимое

JWT
содержит
минимально необходимую информацию.

Персональные данные

не должны
дублироваться
в токене.

---

# Refresh Token

Refresh Token
используется
для получения
нового JWT
без повторного входа.

---

## Основные принципы

Refresh Token:

- хранится
  в базе данных;

- имеет
  значительно больший
  срок действия;

- может быть отозван.

---

## Причины использования

Использование
Refresh Token

позволяет:

- повысить безопасность;

- уменьшить срок жизни JWT;

- выполнять
  принудительный выход
  пользователя.

---

# OAuth2 Client

Система поддерживает
аутентификацию
через внешних поставщиков.

На текущем этапе
используется GitHub OAuth2.

Архитектура допускает
подключение
других OAuth2 Provider
без изменения
предметной области.

---

## Назначение

Предоставить пользователю
возможность входа
без создания
локального пароля.

---

## Основные принципы

OAuth2 Client:

- используется
  только
  для аутентификации;

- не заменяет
  механизм авторизации;

- после успешного входа
  пользователь
  получает
  внутренний Security Context.

---

## Поддержка новых Provider

Добавление нового Provider

не требует
изменения Domain Layer.

Подключение выполняется
на уровне инфраструктуры.

---

# Password Security

Для локальной аутентификации
используются
только безопасные
методы хранения паролей.

---

## Основные принципы

Пароль:

- никогда
  не хранится
  в открытом виде;

- никогда
  не возвращается API;

- никогда
  не записывается
  в журнал событий.

---

## Хеширование

Пароли
хранятся
в виде криптографического хеша.

Используемый алгоритм
должен поддерживаться
Spring Security
и считаться
актуальным
на момент реализации.

---

## Изменение пароля

После смены пароля

действующие Refresh Token

могут быть
принудительно отозваны.

---

# API Security

Все защищенные API
требуют
успешной аутентификации.

---

## Общие принципы

Каждый запрос
обрабатывается независимо.

Состояние аутентификации
не должно зависеть
от предыдущих запросов.

---

## Авторизация

Доступ к ресурсам

проверяется
на основании роли
и принадлежности данных.

---

## Валидация

Все входящие данные

подлежат обязательной проверке.

Недоверенный ввод

никогда
не используется
без проверки.

---

# Session и Cookies

Основным механизмом
аутентификации API

является JWT.

Использование HTTP Session
допускается
только там,
где это необходимо
для интеграции
с внешними механизмами
аутентификации.

---

## Cookies

При использовании Cookie

должны применяться
актуальные рекомендации
по безопасности.

---

## Основные принципы

Cookie:

- имеют ограниченную область действия;

- используют
  HttpOnly
  там,
  где это применимо;

- используют
  Secure
  при работе через HTTPS;

- используют
  актуальную политику SameSite.

---

# Security Headers

Приложение
должно использовать
актуальные HTTP-заголовки безопасности.

---

## Рекомендуемые механизмы

- Content Security Policy;

- X-Content-Type-Options;

- Referrer Policy;

- Permissions Policy;

- Strict-Transport-Security
  (при использовании HTTPS).

---

## Основные принципы

Конкретный набор заголовков

может изменяться

по мере развития
стандартов безопасности.

Архитектура
не должна зависеть
от конкретных значений.

---

# Secrets Management

Все секреты приложения
должны храниться
вне исходного кода.

---

## К секретам относятся

- JWT Secret;

- OAuth2 Client Secret;

- SMTP Credentials;

- MinIO Credentials;

- параметры подключения
  к базе данных;

- другие конфиденциальные данные.

---

## Основные принципы

Секреты:

- не хранятся
  в Git;

- не размещаются
  в исходном коде;

- не фиксируются
  в журнале событий.

---

## Источники конфигурации

Конкретный способ
хранения секретов

зависит
от среды выполнения.

Архитектура допускает
использование:

- переменных окружения;

- внешних хранилищ секретов;

- специализированных
  систем управления секретами.
