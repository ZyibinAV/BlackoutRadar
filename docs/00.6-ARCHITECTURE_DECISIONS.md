# Architecture Decisions — Current Rules

> Компактный индекс действующих архитектурных решений BlackoutRadar.
>
> Этот документ фиксирует **текущее обязательное состояние архитектуры**.
> Полные ADR содержат причины решений, рассмотренные варианты и последствия.
>
> **Источник истины для текущих архитектурных правил:** данный документ + соответствующие полные ADR при необходимости.

---

## Назначение

`00.6-ARCHITECTURE_DECISIONS.md` используется как постоянная компактная карта архитектурных решений проекта.

Документ:

* не заменяет полные ADR;
* не содержит исторический процесс принятия решений;
* не содержит подробную реализацию;
* не определяет TASK;
* не заменяет `01-ARCHITECTURE`, `02-DOMAIN_MODEL`, `03-DATABASE` и другие предметные документы;
* фиксирует только актуальные правила, которые необходимо соблюдать при разработке.

Если решение изменяется, создается или принимается новый ADR. После его принятия данный документ обновляется.

# Действующие архитектурные решения

## Local Authentication

Local Authentication реализуется
в Security/Application boundary.

Domain User не содержит passwordHash.

Локальная регистрация использует
атомарную операцию UserPort.register(...),
создающую User и passwordHash.

Конкурентная регистрация
защищается Database unique constraint(email).

Authentication использует
стандартный Spring Security flow:

AuthenticationManager
→ AuthenticationProvider
→ PasswordEncoder
→ Authentication
→ SecurityContext.

Отдельный PasswordCredentialPort
не вводится.

Полное описание:
07-SECURITY.md

## ADR-001 — Domain First Architecture

**Статус:** Accepted

**Текущее правило:**

Предметная область является центром архитектуры.

Направление зависимостей:

```text
Infrastructure
      ↓
Application
      ↓
Domain
```

Domain не зависит от Spring, Spring Boot, JPA, Hibernate, PostgreSQL, Liquibase, MapStruct, Lombok и других инфраструктурных технологий.

Domain Ports принадлежат внутреннему слою. Реализация Ports находится во внешних слоях.

**Ключевое ограничение:**

Инфраструктурная технология не должна становиться частью Business Domain Model.

**Полный ADR:**

`docs/adr/ADR-001-Domain-First-Architecture.md`

## ADR-002 — Canonical Address Model

**Статус:** Accepted

**Текущее правило:**

В системе используется структурированная каноническая модель адреса.

```text
Region
    ↓
RegionalDistrict (0..1)
    ↓
City
    ↓
Street
    ↓
Address
```

`CityDistrict` является необязательным контекстом внутри `City` и может входить в `Address`.

`Street` принадлежит `City`, а не `CityDistrict`.

Каноническая идентичность:

```text
Street:
City + StreetType + CanonicalName

Address:
Street + CityDistrict + CanonicalHouse
```

Строковое представление адреса не является источником истины.

`House` является Value Object.

**Ключевое ограничение:**

Изменение канонической адресной модели допускается только через новый ADR.

**Полный ADR:**

`docs/adr/ADR-002-Canonical-Address-Model.md`

## ADR-003 — Outage Processing Pipeline

**Статус:** Accepted

**Текущее правило:**

Обработка отключения выполняется через единый конвейер:

```text
ParsedOutage
    ↓
DuplicateResolver
    ↓
PowerOutage
    ↓
CandidateFinder
    ↓
Matching Engine
    ↓
Match
    ↓
Application / Processing Flow
    ↓
Notification
    ↓
Notification Engine
    ↓
NotificationDelivery
    ↓
Retry Processing
    ↓
DeliveryPort
    ↓
Channel Registry
    ↓
Delivery Adapter
    ↓
External Delivery Provider
```

Каждый этап имеет одну ответственность.

`Matching Engine` заканчивает работу формированием `Match`.

`Matching Engine`:

* не создает Notification;
* не выбирает канал;
* не вызывает Delivery Adapter;
* не зависит от Retry Policy.

`Application / Processing Flow` связывает `Match` с созданием `Notification`.

`NotificationDelivery` и `DeliveryAttempt` не являются частью состояния `Notification`.

**Ключевое ограничение:**

Изменение общей структуры Pipeline допускается только через новый ADR.

**Полный ADR:**

`docs/adr/ADR-003-Outage-Processing-Pipeline.md`

## ADR-004 — OutageProvider Architecture

**Статус:** Accepted

**Текущее правило:**

Получение данных от внешних источников отделено от дальнейшего Outage Processing Pipeline.

Поток:

```text
Source
    ↓
Scheduler
    ↓
Provider Registry
    ↓
ProviderContext
    ↓
OutageProvider
    ↓
Provider Technology
    ↓
Adapter
    ↓
ParsedOutage
```

`OutageProvider` использует:

```text
providerType()
fetch(ProviderContext)
    → List<ParsedOutage>
```

`ProviderContext` содержит `sourceId` и конфигурацию.

`ParsedOutage` содержит `sourceId`, а не ссылку на `Source`.

Provider Registry предоставляет поиск Provider по `providerType`.

Ошибки и параллельные запуски одного Source изолируются на уровне Scheduler/Application.

**Ключевое ограничение:**

Замена Scrapy, Botasaurus, AnyDoc или другого внешнего инструмента не должна менять Domain Model и внутренние бизнес-контракты.

Изменение общей OutageProvider Architecture допускается только через новый ADR.

**Полный ADR:**

`docs/adr/ADR-004-OutageProvider-Architecture.md`

## ADR-005 — PowerOutage Event Model

**Статус:** Accepted

**Текущее правило:**

`PowerOutage` является Aggregate Root.

`PowerOutageAddress` принадлежит `PowerOutage` aggregate.

Коллекции внутри aggregate имеют неизменяемую семантику.

Domain invariants и связи aggregate должны сохраняться независимо от Persistence implementation.

**Ключевое ограничение:**

Изменение модели `PowerOutage` как aggregate или его основных бизнес-инвариантов требует отдельного архитектурного решения.

**Полный ADR:**

`docs/adr/ADR-005-PowerOutage-Event-Model.md`

## ADR-006 — Matching Engine

**Статус:** Accepted

**Текущее правило:**

`Matching Engine` принимает окончательное решение о соответствии `PowerOutage` и `Subscription`.

Сопоставление выполняется по каноническим данным.

Строковые сравнения не являются основой Matching.

`CandidateFinder` выполняет предварительный поиск потенциальных Subscription и не принимает окончательное решение.

Результат Matching:

```text
Match
```

`Matching Engine` не создает Notification и не выполняет доставку.

Информация о TransformerStation является дополнительным критерием. При ее отсутствии совпадение может определяться по адресу.

**Ключевое ограничение:**

Изменение алгоритма сопоставления допускается только через новый ADR.

**Полный ADR:**

`docs/adr/ADR-006-Matching-Engine.md`

## ADR-007 — Replaceable Infrastructure

**Статус:** Accepted

**Текущее правило:**

Инфраструктура является заменяемой.

Допускается замена:

* PostgreSQL;
* Persistence implementation;
* Scheduler;
* Provider;
* Email;
* Telegram;
* Delivery Adapter;
* внешних библиотек;
* других инфраструктурных технологий.

Замена инфраструктурного компонента не должна требовать изменения Business Domain Model без архитектурной необходимости.

**Ключевое ограничение:**

Конкретная технология не должна проникать во внутренние Domain contracts.

**Полный ADR:**

`docs/adr/ADR-007-Replaceable-Infrastructure.md`

## ADR-008 — MapStruct SPI Build Infrastructure

**Статус:** Accepted

**Текущее правило:**

Custom MapStruct SPI является отдельной build-time infrastructure.

Модуль:

```text
blackoutradar-mapstruct-spi
```

используется через annotation processor classpath.

SPI:

* не является Domain;
* не является Application;
* не является Persistence runtime component;
* не является Spring component;
* не входит в runtime dependency graph;
* не входит в executable Boot JAR.

MapStruct используется для Domain ↔ Persistence mapping.

**Ключевое ограничение:**

Build-time SPI не должен превращаться в runtime или Domain dependency.

**Полный ADR:**

`docs/adr/ADR-008-MapStruct-SPI-Build-Infrastructure.md`

## ADR-009 — RefreshToken Security Boundary

**Статус:** Accepted

**Текущее правило:**

`RefreshToken` не является частью Business Domain Model.

Он принадлежит Security/Application boundary.

Domain не содержит:

* RefreshToken Entity;
* raw refresh token;
* tokenHash;
* token expiration state;
* token revocation state;
* token rotation state;
* RefreshToken-specific Domain Port.

Security отвечает за:

* Refresh Token lifecycle;
* Access Token lifecycle;
* JWT;
* authentication credentials;
* token validation;
* revocation;
* rotation.

Таблица `refresh_token` может существовать в Database Model.

Persistence и lifecycle решения данного ADR
уточнены более поздним ADR-016
(Rotation Family, `family_id`, rotation,
replay detection, Liquibase changeset);
сама Security Boundary остается в силе.

**Ключевое ограничение:**

Security-specific state не должен проникать в Business Domain Model.

**Полный ADR:**

`docs/adr/ADR-009-RefreshToken Security Boundary.md`

**Уточняющий ADR:**

`docs/adr/ADR-016-Refresh-Token-Rotation-Family-and-Replay-Protection.md`

## ADR-010 — Canonical Address Resolution and Concurrent Creation

**Статус:** Accepted

**Текущее правило:**

Для canonical Address Catalog используется специализированная операция:

```text
resolveCanonical
```

Она означает:

> вернуть существующий canonical object либо атомарно создать его, если объект с такой canonical identity отсутствует.

`resolveCanonical` не является generic CRUD API.

`save` сохраняет обычную persistence semantics.

Canonical identity определяется ADR-002.

Application Layer отвечает за orchestration.

Persistence Adapter отвечает за atomic concurrent resolution.

Для PostgreSQL используется:

```text
INSERT ... ON CONFLICT DO NOTHING
        ↓
canonical SELECT
```

Database UNIQUE constraints обеспечивают concurrent correctness.

Application Layer не использует `DataIntegrityViolationException` как штатный механизм конкурентного создания.

JVM locks и `synchronized` для этой задачи не используются.

**Ключевое ограничение:**

Canonical identity не изменяется внутри implementation TASK. Ее изменение требует нового ADR.

**Полный ADR:**

`docs/adr/ADR-010 — Canonical Address Resolution and Concurrent Creation.md`

## ADR-011 — Notification Channels and Extensible Delivery

**Статус:** Accepted

**Текущее правило:**

`NotificationChannel` является отдельной моделью пользовательской настройки.

Один User может иметь:

* несколько каналов;
* несколько каналов одного типа.

Уникальность:

```text
UNIQUE(user_id, type, destination)
```

`Notification` не содержит канал.

`Subscription` не содержит канал.

Domain не зависит от конкретных Email / Telegram / SMS технологий.

Новый канал должен быть заменяемым инфраструктурным компонентом.

ADR-011 не определяет Retry Policy, Delivery Attempt и окончательную модель Delivery — они определяются ADR-012 и ADR-013.

**Ключевое ограничение:**

Добавление канала не должно изменять Notification Domain, Matching Engine или Parser.

**Полный ADR:**

`docs/adr/ADR-011-Notification Channels and Extensible Delivery.md`

## ADR-012 — Retry and Delivery Attempt Processing

**Статус:** Accepted

**Текущее правило:**

Для доставки используется отдельная модель:

```text
Notification
    │
    │ 1:N
    ↓
NotificationDelivery
    │
    │ 1:N
    ↓
DeliveryAttempt
```

Ответственности:

`Notification`:

* бизнес-потребность в уведомлении;
* Subscription;
* PowerOutage;
* message;
* собственный lifecycle.

`NotificationDelivery`:

* конкретная доставка одного Notification через конкретный NotificationChannel;
* текущее состояние доставки;
* Retry state.

`DeliveryAttempt`:

* неизменяемый факт отдельной попытки доставки.

Retry выполняется на уровне `NotificationDelivery`.

`Notification` не содержит:

* retry count;
* nextAttemptAt;
* DeliveryAttempt;
* NotificationChannel;
* ownership token.

Delivery Adapter выполняет техническую доставку и классифицирует результат:

```text
SUCCESS 
TEMPORARY_FAILURE
PERMANENT_FAILURE
```

Retry Scheduler не принимает бизнес-решений.

**Ключевое ограничение:**

Retry state не должен возвращаться в `Notification`.

**Полный ADR:**

`docs/adr/ADR-012-Retry and Delivery Attempt Processing.md`

## ADR-013 — Retry Policy, Fencing and Recovery

**Статус:** Accepted

**Текущее правило:**

Retry Policy находится в Application Layer.

Текущая политика:

```text
max attempts = 3

after attempt 1 → +1 minute
after attempt 2 → +5 minutes
after attempt 3 → no retry

max delay = 15 minutes
jitter = disabled
```

`NotificationDelivery` обрабатывается через атомарный claim.

Для защиты от устаревшего worker используется `processingToken`.

Финальное сохранение допускается только при совпадении:

```text
delivery id
AND PROCESSING status
AND ownership token
```

Устаревший worker не может перезаписать состояние, захваченное новым worker.

Recovery переводит зависшую:

```text
PROCESSING → READY
```

и очищает ownership token.

Незавершенная `DeliveryAttempt` при Recovery не удаляется и не изменяется.

Архитектура допускает at-least-once delivery и, следовательно, возможна повторная внешняя доставка после аварийного завершения worker.

Порядок Retry Processing:

```text
claim
  ↓
next attempt number
  ↓
create DeliveryAttempt
  ↓
DeliveryPort
  ↓
classify result
  ↓
complete attempt
  ↓
RetryPolicy
  ↓
SENT / FAILED / READY
```

**Ключевое ограничение:**

Нельзя заменять fencing, atomic claim или Recovery JVM-locks, `synchronized` или другими in-memory механизмами.

Изменение claim/fencing/recovery semantics требует отдельного ADR.

**Полный ADR:**

`docs/adr/ADR-013 — Retry Policy, Fencing and Recovery.md`

## ADR-014 — Concurrent Notification Finalization

**Статус:** Accepted

**Текущее правило:**

После успешного fenced-завершения `NotificationDelivery` выполняется финализация соответствующего `Notification`.

Финализация:

1. выполняется только после успешного fenced update конкретной `NotificationDelivery`;
2. получает короткую блокировку строки соответствующего `Notification` в PostgreSQL;
3. повторно читает актуальное состояние всех связанных `NotificationDelivery`;
4. принимает итоговое решение по их текущим состояниям.

Правила:

```text
есть READY или PROCESSING
        ↓
Notification = PROCESSING
```

```text
все NotificationDelivery → SENT
        ↓
Notification = SENT
```

```text
все NotificationDelivery завершены
и хотя бы одна → FAILED
        ↓
Notification = FAILED
```

Сериализуется только короткое принятие итогового решения для `Notification`.

Сами `NotificationDelivery` продолжают обрабатываться независимо и могут выполняться параллельно.

Для финализации не используются:

* `synchronized`;
* JVM locks;
* `ReentrantLock`;
* in-memory locks;
* другие JVM-only механизмы конкурентной защиты.

`processingToken` и fencing продолжают защищать отдельную `NotificationDelivery`. Финализация `Notification` является отдельным механизмом и не заменяет fencing.

Новые состояния `Notification` не вводятся.

**Ключевое ограничение:**

Итоговое состояние `Notification` нельзя определять только по результату одной завершившейся `NotificationDelivery`.

Финальное решение принимается после сериализованной проверки актуального состояния всех доставок.

**Полный ADR:**

`docs/adr/ADR-014-Concurrent-Notification-Finalization.md`

# Правила изменения архитектуры

1. Если задача требует изменения действующего архитектурного решения — сначала Architecture First.
2. Если существующего ADR недостаточно — создается новый ADR.
3. Новый ADR не переписывает историю старого ADR.
4. Если новый ADR заменяет старое решение, старый ADR получает соответствующий статус `Superseded`.
5. После принятия нового ADR необходимо обновить этот индекс.
6. Затем обновляются затронутые текущие архитектурные документы.
7. Только после этого архитектурное решение используется как основание для TASK.
8. OpenCode не принимает архитектурные решения самостоятельно.
