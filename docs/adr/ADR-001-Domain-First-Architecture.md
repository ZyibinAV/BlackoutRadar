# ADR-001 — Domain First Architecture

**Статус:** Accepted

**Дата:** 2026-08-04

**Версия:** 1.0

---

# Назначение

Зафиксировать основной архитектурный принцип проекта BlackoutRadar,
согласно которому предметная область является центром системы,
а все инфраструктурные компоненты рассматриваются как внешние зависимости.

Данный документ является основополагающим архитектурным решением проекта.

---

# Контекст

BlackoutRadar предназначен для автоматического мониторинга плановых отключений
электроэнергии.

Система должна:

- получать информацию из различных внешних источников;
- нормализовать полученные данные;
- сопоставлять отключения с подписками пользователей;
- отправлять уведомления.

На этапе проектирования возник вопрос:

> Что должно являться центром архитектуры проекта?

Были рассмотрены два подхода:

- Infrastructure First
- Domain First

От данного выбора зависит дальнейшая архитектура всей системы.

---

# Проблема

Во многих Spring Boot проектах бизнес-логика постепенно начинает зависеть
от инфраструктуры:

- Spring Framework;
- JPA;
- конкретной базы данных;
- парсеров;
- внешних API;
- механизмов уведомлений.

В результате изменение любого инфраструктурного компонента приводит
к изменению бизнес-логики.

Для BlackoutRadar подобная зависимость является нежелательной,
поскольку система должна иметь возможность:

- подключать новые источники данных;
- изменять способы получения информации;
- расширять способы уведомлений;
- изменять инфраструктуру без изменения предметной области.

---

# Рассмотренные варианты

## Вариант 1 — Infrastructure First

Архитектура строится вокруг используемых технологий.

Типичная схема:

```text
Controller
    │
    ▼
Service
    │
    ▼
Repository
    │
    ▼
Database
```

### Преимущества

- простая реализация;
- минимальный порог входа;
- привычная структура большинства CRUD-проектов.

### Недостатки

- высокая связанность компонентов;
- зависимость бизнес-логики от Spring Framework;
- сложность замены инфраструктуры;
- ухудшение тестируемости;
- нарушение Dependency Inversion Principle.

---

## Вариант 2 — Domain First

Архитектура строится вокруг предметной области.

```text
                 Domain
                    ▲
                    │
             Application Layer
                    ▲
                    │
Infrastructure (Spring, Database, Providers)
```

Инфраструктура рассматривается как внешний слой,
обеспечивающий работу доменной модели.

### Преимущества

- независимость бизнес-логики;
- высокая расширяемость;
- простота модульного тестирования;
- возможность замены инфраструктурных компонентов;
- соответствие принципам SOLID;
- соответствие принципам Clean Architecture.

### Недостатки

- более сложная первоначальная архитектура;
- большее количество абстракций;
- увеличение времени первоначального проектирования.

---

# Принятое решение

В проекте BlackoutRadar используется архитектурный подход
**Domain First**.

Предметная область является центральной частью системы.

Все инфраструктурные компоненты взаимодействуют
с предметной областью исключительно через определенные абстракции.

В частности:

- источники данных реализуют интерфейс `OutageProvider`;
- механизм уведомлений инкапсулирован в Notification Engine;
- алгоритмы сопоставления полностью независимы от способов получения данных;
- инфраструктурные сервисы не содержат бизнес-логики.

---

# Архитектурные последствия

После принятия данного решения вся система строится вокруг следующих принципов.

## 1. Предметная область независима

Доменные модели не должны зависеть от:

- Spring Framework;
- JPA;
- PostgreSQL;
- MinIO;
- SMTP;
- Telegram;
- HTML-парсеров;
- сторонних библиотек.

---

## 2. Инфраструктура заменяема

Любой внешний компонент должен иметь возможность
быть замененным без изменения предметной области.

Например:

- HTML → REST API;
- собственный парсер → open-source parser;
- Email → Telegram;
- PostgreSQL → другая СУБД.

---

## 3. Бизнес-логика располагается только в Domain Layer

Алгоритмы:

- нормализации адресов;
- дедупликации;
- сопоставления;
- принятия решений;

являются частью предметной области.

---

## 4. Внешние системы подключаются через адаптеры

Предметная область не взаимодействует напрямую
с внешними библиотеками.

Все интеграции выполняются через Adapter Layer.

---

# Причины выбора

Выбранный подход обеспечивает:

- независимость предметной области;
- простоту расширения проекта;
- высокую тестируемость;
- возможность постепенной замены инфраструктуры;
- долгосрочную сопровождаемость.

Для проекта BlackoutRadar эти требования являются более важными,
чем минимизация первоначальной сложности архитектуры.

---

# Положительные последствия

После принятия данного решения система получает следующие преимущества:

- независимость бизнес-логики;
- модульность;
- расширяемость;
- низкую связанность компонентов;
- возможность подключения новых источников данных;
- возможность замены способов уведомлений;
- простоту написания unit-тестов;
- соответствие современным архитектурным практикам.

---

# Отрицательные последствия

Принятое решение приводит к:

- увеличению количества абстракций;
- более сложной структуре проекта;
- большему объему первоначального проектирования;
- более высокому порогу входа для новых разработчиков.

Данные недостатки признаны допустимыми.

---

# Влияние на реализацию

Настоящее решение оказывает влияние практически
на все подсистемы проекта.

В первую очередь:

- Domain Model;
- OutageProvider;
- AddressService;
- DuplicateResolver;
- Matching Engine;
- Notification Engine;
- Scheduler;
- Adapter Layer.

Все последующие архитектурные решения
должны соответствовать данному ADR.
