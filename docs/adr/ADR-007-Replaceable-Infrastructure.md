# ADR-007 — Replaceable Infrastructure

**Статус:** Accepted

**Дата:** 2026-08-08

**Версия:** 1.0

---

# Назначение

Зафиксировать архитектурное решение,
согласно которому инфраструктурные компоненты
не являются частью предметной области
и могут быть заменены
без изменения бизнес-логики.

Данный документ определяет отношение системы
к внешним технологиям
и инфраструктуре.

---

# Контекст

BlackoutRadar использует
различные инфраструктурные компоненты.

Например:

- PostgreSQL;
- Spring Framework;
- Spring Security;
- MinIO;
- SMTP;
- Telegram;
- Scheduler;
- open-source parser;
- REST API.

Все перечисленные компоненты
являются средствами реализации,
но не частью предметной области.

---

# Проблема

Если предметная область
начинает зависеть
от инфраструктуры,

то изменение
или замена
любого компонента
приводит
к изменению
бизнес-логики.

Подобная архитектура
усложняет развитие проекта
и нарушает
основные принципы
Domain First Architecture.

---

# Рассмотренные варианты

## Вариант 1 — Жесткая зависимость

```
Domain

↓

Spring

↓

Database

↓

Provider
```

Предметная область
использует
конкретные технологии.

### Преимущества

- простая реализация;
- меньшее количество абстракций.

### Недостатки

- сильная связанность;
- сложность тестирования;
- невозможность замены компонентов;
- нарушение Dependency Inversion Principle.

---

## Вариант 2 — Replaceable Infrastructure

```
Domain

↓

Ports

↓

Adapters

↓

Infrastructure
```

Предметная область
зависит
только
от собственных абстракций.

Инфраструктура
подключается
через адаптеры.

### Преимущества

- независимость Domain Layer;
- высокая расширяемость;
- простота тестирования;
- возможность постепенной замены компонентов;
- долгосрочная сопровождаемость.

### Недостатки

- дополнительные интерфейсы;
- увеличение количества компонентов;
- более сложная первоначальная архитектура.

---

# Принятое решение

В проекте используется
Replaceable Infrastructure.

Ни один инфраструктурный компонент
не является обязательной частью
предметной области.

Все зависимости
от внешних технологий
инкапсулируются
в инфраструктурном слое.

---

# Архитектурные принципы

## 1. Предметная область не знает инфраструктуру

Domain Layer
не зависит
от:

- Spring Framework;
- Spring Boot;
- Hibernate;
- PostgreSQL;
- MinIO;
- SMTP;
- Telegram;
- Jsoup;
- PDFBox;
- сторонних библиотек.

---

## 2. Все внешние зависимости подключаются через абстракции

Предметная область
работает
только
с собственными интерфейсами.

---

## 3. Замена инфраструктуры не влияет на бизнес-логику

Допускается замена:

- PostgreSQL;
- MinIO;
- Email;
- Telegram;
- Scheduler;
- Provider;
- способов хранения файлов;
- способов получения данных.

Изменение инфраструктуры
не должно изменять
предметную область.

---

## 4. Инфраструктура не содержит бизнес-логики

Инфраструктурные компоненты
отвечают только
за взаимодействие
с внешними системами.

---

## 5. Бизнес-логика полностью сосредоточена
в Domain Layer

Все решения
о сопоставлении,
дедупликации,
нормализации
и обработке событий

принимаются
в предметной области.

---

# Причины выбора

Выбранный подход обеспечивает:

- независимость архитектуры;
- возможность развития проекта;
- простоту модульного тестирования;
- возможность замены технологий;
- соответствие Clean Architecture.

---

# Положительные последствия

После принятия решения:

- легко обновляются технологии;
- уменьшается связанность компонентов;
- упрощается сопровождение;
- увеличивается срок жизни архитектуры;
- уменьшается риск дорогостоящих рефакторингов.

---

# Отрицательные последствия

Решение приводит к:

- увеличению количества интерфейсов;
- дополнительным слоям абстракции;
- более сложной первоначальной реализации.

Данные недостатки признаны допустимыми.

---

# Влияние на реализацию

Настоящее решение оказывает влияние
на следующие подсистемы:

- Persistence;
- Security;
- Storage;
- Notification;
- Provider;
- Scheduler;
- Adapter Layer.

Все инфраструктурные компоненты
обязаны соответствовать
данному ADR.
