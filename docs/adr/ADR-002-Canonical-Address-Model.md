# ADR-002 — Canonical Address Model

**Статус:** Accepted

**Дата:** 2026-08-06

**Версия:** 1.0

---

# Назначение

Зафиксировать архитектурное решение,
определяющее способ хранения,
нормализации
и использования адресов
в системе BlackoutRadar.

Данный документ определяет единое представление адресов
во всей системе.

---

# Контекст

Основная задача BlackoutRadar —
определение соответствия
между отключениями электроэнергии
и подписками пользователей.

Информация об адресах поступает
из различных источников:

- сайты энергокомпаний;
- PDF-документы;
- DOCX;
- RTF;
- пользовательский ввод;
- внешние сервисы.

Каждый источник использует собственный формат записи адресов.

Например:

```
ул. Ленина, 15

Ленина 15

г. Омск, ул. Ленина, д.15

улица Ленина 15

ЛЕНИНА,15
```

Все приведенные варианты
описывают один и тот же адрес.

Использование строкового сравнения
делает надежное сопоставление невозможным.

---

# Проблема

Необходимо обеспечить:

- единое представление адресов;
- отсутствие дубликатов;
- быстрый поиск;
- корректное сопоставление данных
  из различных источников.

При этом архитектура должна
поддерживать расширение системы
без изменения существующей модели.

---

# Рассмотренные варианты

## Вариант 1 — Строковое хранение адресов

```
Address

addressText
```

### Преимущества

- минимальная сложность;
- простая реализация.

### Недостатки

- большое количество дубликатов;
- невозможность корректного сравнения;
- отсутствие структурированного поиска;
- зависимость алгоритмов
  от формата записи.

---

## Вариант 2 — Частичная нормализация

```
City

Address
```

где Address содержит название улицы
и номер дома.

### Преимущества

- небольшое количество сущностей;
- простая реализация.

### Недостатки

- дублирование улиц;
- невозможность обеспечить
  единообразие названий;
- сложная нормализация.

---

## Вариант 3 — Каноническая адресная модель

```
Region
    │
    ▼
City
    │
    ▼
Street
    │
    ▼
Address
```

Все элементы адреса
представлены отдельными сущностями.

Названия улиц
и номера домов
нормализуются
до сохранения.

### Преимущества

- отсутствие дубликатов;
- единое представление адресов;
- быстрый поиск;
- эффективное сопоставление;
- высокая расширяемость.

### Недостатки

- большее количество сущностей;
- более сложная первоначальная реализация.

---

# Принятое решение

В проекте используется
каноническая адресная модель.

Адрес всегда хранится
в структурированном виде.

Строковое представление
не используется
в качестве источника истины.

---

# Архитектурные принципы

## 1. Адрес всегда структурирован

Используется следующая модель:

```
Region
    │
    ▼
City
    │
    ▼
Street
    │
    ▼
Address
```

---

## 2. Street является самостоятельной сущностью

Улица входит
в адресный каталог.

Создание новых улиц
происходит автоматически
при необходимости.

Предварительное заполнение
всего справочника
не требуется.

---

## 3. Названия улиц нормализуются

Перед сохранением
выполняется нормализация названия.

В системе существует
единственное каноническое представление улицы.

---

## 4. Дом хранится в структурированном виде

Адрес разделяет номер дома
на две части:

- houseNumber
- houseAddition

Дополнительно хранится
каноническое представление дома,
используемое при поиске.

---

## 5. Адрес создается только одним способом

Создание Address
выполняется
только через AddressService.

Прямое создание адресов
другими компонентами системы
не допускается.

---

## 6. Сырой адрес не является частью доменной модели

Адрес,
полученный
от пользователя
или внешнего источника,

используется
только
во время обработки.

После завершения нормализации
система работает
исключительно
с каноническим адресом.

---

# Причины выбора

Каноническая адресная модель обеспечивает:

- единый формат хранения;
- отсутствие дубликатов;
- независимость алгоритмов
  от способа записи адреса;
- быстрый поиск;
- эффективную работу Matching Engine;
- возможность подключения новых источников данных.

---

# Положительные последствия

После принятия данного решения:

- уменьшается количество дубликатов;
- упрощается сопоставление;
- повышается качество поиска;
- снижается сложность алгоритмов;
- повышается качество данных.

---

# Отрицательные последствия

Решение приводит к:

- усложнению модели данных;
- необходимости нормализации;
- увеличению количества сервисов;
- большему количеству первоначальной логики.

Данные недостатки признаны допустимыми.

---

# Влияние на реализацию

Настоящее решение оказывает влияние
на следующие компоненты системы:

- Address;
- Street;
- Region;
- City;
- Subscription;
- PowerOutageAddress;
- AddressService;
- StreetNormalizer;
- HouseNormalizer;
- Matching Engine;
- DuplicateResolver.
