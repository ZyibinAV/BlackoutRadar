# ADR-006 — Matching Engine

**Статус:** Accepted

**Дата:** 2026-08-08

**Версия:** 1.0

---

# Назначение

Зафиксировать архитектурное решение,
определяющее алгоритм сопоставления
событий отключения электроэнергии
с подписками пользователей.

Matching Engine является
основным компонентом
предметной области BlackoutRadar.

---

# Контекст

После обработки информации
об отключении электроэнергии
необходимо определить,
относится ли данное событие
к конкретной подписке пользователя.

Система должна учитывать:

- адрес;
- трансформаторную подстанцию;
- период мониторинга;
- правила сопоставления.

Количество пользователей
может значительно увеличиваться,
поэтому алгоритм
должен быть масштабируемым.

---

# Проблема

Прямое последовательное сравнение
каждого отключения
со всеми подписками

приводит к:

- низкой производительности;
- сложной логике;
- плохой расширяемости.

Необходимо определить
универсальный механизм сопоставления,
не зависящий
от конкретных источников данных.

---

# Рассмотренные варианты

## Вариант 1 — Полное последовательное сравнение

```
PowerOutage

↓

Все Subscription

↓

Совпало / Не совпало
```

### Преимущества

- простая реализация.

### Недостатки

- плохая производительность;
- сложность расширения;
- большое количество лишних проверок.

---

## Вариант 2 — Pipeline сопоставления

```
PowerOutage

↓

CandidateFinder

↓

Matching Engine

↓

Match
```

Предварительно
отбираются только потенциальные кандидаты,
после чего выполняется
детальная проверка.

### Преимущества

- высокая производительность;
- масштабируемость;
- разделение ответственности;
- простота расширения.

### Недостатки

- большее количество компонентов.

---

# Принятое решение

В проекте используется
двухэтапный алгоритм сопоставления.

Сначала выполняется
поиск кандидатов,

после чего
Matching Engine
проверяет
правила совпадения.

---

# Архитектурные принципы

## 1. Поиск кандидатов выполняется отдельно

CandidateFinder

не определяет совпадение.

Его задача —

максимально уменьшить
количество подписок,
которые необходимо проверить.

---

## 2. Matching Engine содержит только бизнес-логику

Matching Engine
не взаимодействует

- с Provider;
- с базой данных;
- с механизмами уведомлений.

Он отвечает
только за принятие решения.

---

## 3. Сопоставление выполняется
по каноническим данным

Все сравнения выполняются
только
между нормализованными объектами.

Строковые сравнения
не допускаются.

---

## 4. Информация о ТП является дополнительным критерием

Если информация
о трансформаторной подстанции
отсутствует
в источнике данных,

совпадение определяется
по адресу.

Отсутствие информации
не считается
отрицательным совпадением.

---

## 5. Результатом является Match

Matching Engine
не отправляет уведомления.

Он только сообщает,
что найдено совпадение.

---

## 6. Notification Engine работает независимо

Создание уведомления
является следующим этапом Pipeline.

Matching Engine
не зависит
от способа доставки сообщений.

---

# Причины выбора

Выбранная архитектура обеспечивает:

- высокую производительность;
- простоту расширения;
- независимость компонентов;
- высокую тестируемость;
- соответствие Domain First Architecture.

---

# Положительные последствия

После принятия решения:

- уменьшается количество проверок;
- ускоряется сопоставление;
- упрощается развитие алгоритмов;
- повышается качество архитектуры.

---

# Отрицательные последствия

Решение приводит к:

- появлению CandidateFinder;
- увеличению количества компонентов;
- более сложной первоначальной архитектуре.

Данные недостатки признаны допустимыми.

---

# Влияние на реализацию

Настоящее решение оказывает влияние
на следующие компоненты:

- CandidateFinder;
- Matching Engine;
- Subscription;
- Address;
- PowerOutage;
- Notification;
- Notification Engine.
